# Датасет IBM AML

Данные синтетические, это [IBM Transactions for Anti Money Laundering](https://www.kaggle.com/datasets/ealtman2019/ibm-transactions-for-anti-money-laundering-aml/data) с Kaggle. Каждая строка это один платёж и метка, отмывание это или нет. Метка известна, поэтому можно обучать обычный классификатор.

Я взял `LI-Small`. Всего вариантов шесть: `HI-Small`, `HI-Medium`, `HI-Large`, `LI-Small`, `LI-Medium`, `LI-Large`. HI и LI это больше или меньше доля отмывания, Small/Medium/Large это размер.

## В чём сложность

Положительных очень мало, и картина меняется от дня к дню. Accuracy тут бесполезна: если всегда говорить «обычный платёж», accuracy будет почти 100%, а отмывание не найдётся вообще. Поэтому я смотрю на Average Precision, precision и recall.

## Колонки

| Поле | Тип после проверки | Что это |
|---|---|---|
| `Timestamp` | datetime | время транзакции |
| `From Bank` | string | банк отправителя |
| `Account` | string | счёт отправителя |
| `To Bank` | string | банк получателя |
| `Account.1` | string | счёт получателя |
| `Amount Received` | numeric | сколько получили |
| `Receiving Currency` | string | в какой валюте получили |
| `Amount Paid` | numeric | сколько отправили |
| `Payment Currency` | string | в какой валюте отправили |
| `Payment Format` | string | формат платежа |
| `Is Laundering` | int8, 0 или 1 | целевая метка |

Счёт всегда беру вместе с банком: один и тот же номер в двух разных банках это разные счета. В CSV обе колонки со счетом называются `Account`, pandas сам переименовывает вторую в `Account.1`.

ID транзакции нет. Поэтому одинаковые строки я не удаляю, это вполне могут быть два настоящих одинаковых платежа.

## Как скачать

```bash
python3 scripts/download_dataset.py
```

Перед этим нужно настроить Kaggle CLI, как это сделать и как потом запустить ETL, написано в [ETL.md](ETL.md).

Сырой файл попадает в `data/raw/LI-Small_Trans.csv`, подготовленные данные в `artifacts/runs/<run_id>/data/`. Обе папки в git не попадают.

## Откуда взялись цифры в отчётах

Полный эксперимент, который лежит в `reports/`, обработал 6 924 041 строку из локального `data/processed/raw.parquet`. Совпадает ли он один в один со скачанным сейчас CSV, я не проверял. Новый ETL записывает SHA256 файла, так что дальше будет видно, на каких именно данных был запуск.

Ещё в датасете нет информации, когда закончилось расследование и метка стала известна. OTE считает, что метки известны сразу. Для реальной системы это так не работает, надо помнить.
